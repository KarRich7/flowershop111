# Архитектура «Цветы Урала» (тестовый MVP)

## 1. Общая схема

```
 Покупатель ──► Next.js (сайт)  ─┐
 Сотрудник ──► Next.js (/admin) ─┤  /api/v1/*  (REST, JSON)
 Telegram  ──► aiogram-адаптер ──┤──────────────►  Django + DRF  ──►  PostgreSQL 16
 ВКонтакте ──► VK Long Poll    ──┘   BotEngine        │  (единая бизнес-логика)
                                                      ├──►  Redis ──► Celery worker / beat
                                                      └──►  Платёжный провайдер (сейчас: тестовый)
```

* **Модульный монолит**: одна кодовая база Django, модули в `backend/apps/*`, общая БД.
* **Боты не имеют своего склада и своих правил.** Адаптеры Telegram и ВК только переводят
  сообщения/кнопки в вызовы общего `BotEngine` (`apps/bots/engine.py`), который работает
  с теми же сервисами корзины, заказов и склада, что и сайт.
* **Канал заказа определяет сервер**, а не клиент: сайт — анонимный запрос (или с HttpOnly-cookie
  вошедшего покупателя `cu_customer`), бот —
  сервисная авторизация `Authorization: Bot <BOT_SERVICE_TOKEN>` + `X-Bot-Channel`.
  Запрет конструктора и поштучных цветов для ботов проверяется в сервисном слое
  (`carts.assert_custom_allowed`, `carts.add_product`), поэтому его нельзя обойти прямым
  вызовом API.
* Страницы-симулятора ботов на сайте больше нет. Отладочный эндпоинт `/api/v1/simulator/*`
  (тот же `BotEngine` с `simulated=True`) включается только `BOT_SIMULATOR_ENABLED=true` — для
  разработки и автотестов; в продакшене выключен.

## 3. База данных (PostgreSQL)

Все обязательные сущности реализованы отдельными таблицами (имена `db_table` совпадают с ТЗ):

| Таблица | Назначение |
|---|---|
| `users` | сотрудники (роль owner / florist / courier), пароли — PBKDF2-хеши |
| `customers`, `customer_channels` | клиенты; привязки к сайту, Telegram, ВК (уникальность channel+external_id) |
| `customer_logins`, `customer_sessions` | запросы входа на сайт через Telegram/ВК (10 мин) и сессии покупателей (хранится только SHA-256 токена, 180 дней) |
| `catalog_categories` | категории витрины (букеты / цветы), порядок задаёт владелец |
| `products`, `product_images` | витрина: букеты, цветы, зелень, упаковка, ленты, открытки, дополнения |
| `inventory_items` | складские позиции: SKU, категория, ед. изм., закупочная цена, цена продажи, мин. остаток, активность |
| `stock_balances` | фактический остаток и резерв; CHECK `quantity ≥ 0`, `reserved ≥ 0`, `reserved ≤ quantity` |
| `stock_movements` | журнал всех движений (поставка, списание, продажа, сборка, корректировка, инвентаризация…) |
| `bouquet_recipes`, `recipe_components` | рецептуры готовых букетов |
| `carts`, `cart_items` | корзины (канал фиксируется при создании) |
| `orders`, `order_items` | заказ + **неизменяемый снимок** состава и цен (JSON-снимок, цены в копейках) |
| `stock_reservations` | резервы под заказы со сроком действия |
| `payments`, `payment_webhook_events` | платежи и журнал уведомлений провайдера (уникальный event id → идемпотентность) |
| `deliveries`, `delivery_zones`, `delivery_slots` | доставка (адрес, координаты, курьер, отметки «адрес узнать у получателя», «сюрприз», «анонимно»), районы и цены, интервалы с лимитом |
| `order_photos` | фото собранного букета от флориста (видны покупателю на странице заказа) |
| `order_events` | история изменений заказа (кто, когда, из какого статуса в какой) |
| `bot_sessions` | состояние диалога бота (шаг оформления, корзина) |
| `notifications` | очередь уведомлений (Telegram / ВК / сотрудникам / SMS) |
| `audit_logs` | журнал действий сотрудников |
| `shop_settings`, `about_photos` | название, логотип, цвета, контакты, график, правила резервов, текст и фото страницы «О нас» |

* Все суммы — целые **копейки** (`PositiveIntegerField`), CHECK `total = items_total + delivery_cost`,
  `line_total = unit_price × quantity`.
* Внешние ключи с `PROTECT` для истории (заказы, движения), индексы по статусам, датам, каналам.
* Строки заказа защищены триггером PostgreSQL от изменений. Единственное разрешённое изменение —
  «отвязать» удалённый владельцем товар/складскую позицию (`product_id`/`inventory_item_id` → NULL);
  название, цена, количество и состав остаются прежними (миграция `orders/0003`).
* Резервирование, списание, подтверждение и отмена выполняются в транзакциях
  с `SELECT … FOR UPDATE` строк `stock_balances` в фиксированном порядке (без взаимных блокировок).

## 4. Ключевые бизнес-правила

**Доступный остаток** = `quantity − reserved` (по `stock_balances`). Один и тот же расчёт
используется сайтом, ботами, конструктором и кассой магазина.

**Готовые букеты.** Букет — отдельная складская единица:
* собран заранее (рецепт → «Собрать») — компоненты списываются при сборке, букет
  приходит на склад; при продаже списывается только сам букет;
* под заказ (`allow_made_to_order`) — при оформлении резервируются компоненты по рецепту,
  списание — по факту сборки (статус «Собирается → Готов»);
* смешанный случай: часть из готовых, недостающее — под заказ.

**Индивидуальный букет (только сайт).** Конструктор — эскиз из настоящих фото: у каждого
цветка, ветки зелени и упаковки есть `constructor_image` (бутон без фона / текстура материала).
Флорист загружает его в карточке товара; однотонный фон убирается на сервере
(`apps/catalog/cutout.py`: цвет фона по краям кадра → прозрачность → очистка кромки → обрезка, WebP).
Два режима: **«С эскизом»** — покупатель сам собирает эскиз; **«По фото»** — выбирает только цветы
(по фото и количеству), бумагу и ленту, а раскладку делает флорист (`composition.florist_choice = true`,
`layout = []`; в заказе и админке вместо эскиза показываются фото позиций с пометкой «Оформит флорист»).
Покупатель добавляет цветы кнопкой «+» (цветок встаёт в свободное место купола по золотой спирали,
`pack()` в `draw.tsx`; при большом числе цветков бутоны уменьшаются, под ними рисуется общий фон)
или перетаскиванием (на телефоне — удержание),
двигает их на эскизе, отражает и поворачивает выбранный цветок (панель над ним, клавиши F, [ ], Delete);
расположение (`layout`: x, y, угол, отражение) сохраняется в заказе, и флорист видит тот же
эскиз. Упаковка рисуется по материалу (бумага, плёнка, фетр, коробка), бант — по ленте
(атлас, шёлк, органза, шпагат); можно выбрать «Без упаковки» — стебли перевязываются лентой.
Оплата индивидуального букета — только онлайн. Сервер проверяет состав (виды цветов из наличия,
число стеблей в пределах настроек, по умолчанию 3–30; больше 30 нельзя — `MAX_CUSTOM_STEMS_LIMIT`), считает цену по текущим ценам + работа флориста
(настраивается), резервирует материалы. Заказ получает статус «Ожидает подтверждения»;
ссылка на онлайн-оплату выдаётся **только после подтверждения флористом**.

**Доставка по зонам на карте.** Зона — набор многоугольников (`DeliveryZone.polygons`,
демо-границы Кондратово, районов Перми и пригорода из OpenStreetMap, ODbL; мастерская — Кондратово, ЖК «Медовый»). Покупатель ищет адрес или ставит
метку на карте (Яндекс Карты JS API 2.1); сервер (`apps/delivery/geo.py`) геокодирует адрес
(Яндекс HTTP Геокодер при наличии ключа, иначе Nominatim), проверяет, что найден конкретный дом
и точка рядом с ним, и определяет зону по точке. Вне всех зон — «Сюда мы не доставляем», заказ
не создаётся. Проверенный адрес подписывается HMAC-токеном, чтобы не геокодировать его повторно.
Доставка бесплатна от `free_from` зоны (по умолчанию 1 500 ₽). Оплата при получении выключена
по умолчанию (`ShopSettings.allow_cash_on_delivery`) и никогда не доступна для индивидуальных букетов.
Если Яндекс отклоняет ключ (403, лимит, сеть), сервер на 10 минут переключается на Nominatim;
владелец видит причину в Настройках → «Карта и поиск адресов» (`apps/delivery/maps_check.py`,
`GET /admin/maps/check`, та же проверка — `manage.py check_maps`).

**Как вручить** (по образцу крупных цветочных сервисов):
* `Delivery.ask_recipient` — покупатель не знает адрес: выбирает только зону (цена по ней) и даёт телефон
  получателя; адрес хранится как «Адрес уточним у получателя (…)» (`address_pending`). Заказ уходит
  в «Ожидает подтверждения»; пока флорист не впишет адрес (`PATCH /admin/orders/{id}/delivery`),
  переходы в оплату/подтверждение/сборку/передачу курьеру запрещены (`409 address_pending`).
  Новый адрес геокодируется; если он в другой зоне — подсказка про доплату (цена в снимке не меняется).
* `Delivery.surprise` — не звонить получателю заранее (несовместимо с `ask_recipient`);
  `Delivery.anonymous` — не называть отправителя. Оба флага видны курьеру на доске доставок.
* `Order.photo_before` — фото букета перед отправкой: флорист загружает `OrderPhoto`, первое фото
  уходит покупателю в мессенджер; без фото переход «Передан курьеру» запрещён (`409 photo_required`).

**Сроки резерва** (настраиваются в админке):
* неоплаченный онлайн-заказ — 15 мин, после чего резерв снимается, заказ отменяется;
* заказ с оплатой при получении: после подтверждения сотрудником **не отменяется таймером**;
  неподтверждённый — отдельный срок (по умолчанию 180 мин, 0 — без авто-отмены);
* ожидающий подтверждения флористом — 24 ч;
* оплата, пришедшая после истечения резерва, автоматически уходит в возврат.

**Предзаказы на дальние даты** (> 2 дней) не резервируют физический остаток — учитываются
как планируемый спрос (раздел «Склад → Спрос»), требуют подтверждения флористом.

**Статусы заказа** — конечный автомат (`apps/orders/state.py`):

```
new → awaiting_confirmation → awaiting_payment → confirmed → assembling → ready
ready → handed_to_courier → delivered → completed
ready → awaiting_pickup → delivered → completed
(до передачи курьеру / выдачи) → cancelled
```
Любой переход вне таблицы отклоняется (HTTP 409). Статус оплаты хранится отдельно:
`unpaid, pending, paid, refund_pending, refunded, failed`.

**Отмена:** до сборки — резервы освобождаются; после сборки готового букета — букет
возвращается на склад; после сборки индивидуального — предупреждение о списании (материалы
уже израсходованы). Оплаченный заказ при отмене переводится в возврат.

**Оплата.** `PaymentProvider` (`apps/payments/providers/base.py`): `create_payment`,
`request_refund`, `parse_webhook`, `fetch_event` (сверка статуса без уведомления), `refund_hint`
(подсказка для ручного возврата), `telegram_invoice` (точка расширения для встроенных счетов
Telegram). Провайдеры: `simulator` (тест), `rollypay` (основной: форма RollyPay, подпись колбэка
HMAC-SHA256 + повторный запрос статуса к API, возвраты вручную), `yookassa` (запасной).
Webhook проверяет подпись и идемпотентен (повторное событие — без эффекта).
Для чека 54-ФЗ данные формируются в `apps/payments/fiscal.py` и сохраняются в платеже.
ВК и Telegram получают **защищённую ссылку** `/pay/<секретный токен>`.

**Вход покупателя через Telegram / ВКонтакте** (`apps/customers/login.py`). Регистрации и паролей
нет; вход необязателен.

```
 Сайт: «Войти через Telegram» ─► POST /account/login/start ─► {code, link} + HttpOnly-cookie cu_login
   │ открывает t.me/<бот>?start=login_<код>  (ВК: vk.me/club<ID>?ref=login_<код>)
   ▼
 Бот (BotEngine._login_hook) ─► «Войти на сайт?» [Войти] [Это не я]
   │ «Войти» → login.confirm(): клиент = тот, кто написал боту (customer_channels)
   ▼
 Сайт опрашивает POST /account/login/status ─► HttpOnly-cookie cu_customer (180 дней; JS её не видит)
```
* Если ссылка не открылась, покупатель отправляет боту 6-значный код; 5 ошибок подряд — блокировка на 30 мин.
* Вход с привязкой `order_token` (со страницы заказа) сразу переносит заказ на этого клиента — статусы
  начинают приходить в мессенджер.
* Подтверждённый в боте вход нужно забрать за те же 10 минут — позже он не превращается в сессию.
* При оформлении с cookie `cu_customer` заказ привязывается к вошедшему клиенту без поиска по
  телефону; имя, телефон, e-mail и последний адрес доставки подставляются в форму в следующий раз
  (`GET /account/me`). Кабинет `/account`: контакты, каналы уведомлений, история заказов, выход
  (на этом устройстве / на всех).
* Тестовый режим `CUSTOMER_LOGIN_TEST_MODE=true` добавляет кнопку «Подтвердить вход (тестовый режим)»
  без мессенджера — только для разработки и e2e.

**Категории и «О нас».** Категории витрины (букеты и цветы) создаются, переименовываются,
сортируются и удаляются в админке (товары при удалении переносятся в другую категорию или остаются
без неё). Страница «О нас» — заголовок, вступление, текст и карусель до 12 фото.

**Приём заказов и тексты сайта** (`ShopSettings`, `apps/core/site_content.py`).
`orders_enabled=false` — единая проверка `carts.services.assert_orders_open()` (корзина, свой букет,
`orders.services` при оформлении, боты) → `409 orders_closed` с сообщением владельца; продажа в
магазине (`store_sale`) не проверяет флаг. `customer_login_enabled` учитывает
`customers.login.channels_available()`. «Частые вопросы» — JSON `faq` (`null` = стандартные из
`default_faq()`), проверка `clean_faq()`. SEO — JSON `seo_pages` поверх `seo_defaults()`; фронтенд
собирает метаданные в `frontend/lib/seo.ts` (title, description, canonical, Open Graph, коды
верификации в `app/layout.tsx`), `app/sitemap.ts` и `app/robots.ts` строятся на каждый запрос.

## 5. Роли и доступ

| Действие | Владелец | Флорист | Курьер |
|---|:-:|:-:|:-:|
| Дашборд и статистика (выручка) | ✓ | ✓ (без финансов) | свои доставки |
| Заказы: просмотр, подтверждение, отмена, курьер | ✓ | ✓ | только назначенные, без сумм |
| Изменение статусов доставки | ✓ | ✓ | только назначенные (передан/доставлен/вернуть) |
| Возвраты | ✓ | — | — |
| Товары, категории, фото, фото для конструктора (вырезание, кадрирование), рецептуры букетов | ✓ | ✓ | — |
| Удаление любого товара навсегда (флорист — только товары без истории, остальные скрывает) | ✓ | — | — |
| Цены продажи, остаток на складе | ✓ | ✓ | — |
| Закупочные цены | ✓ | — | — |
| Склад, поставки, списания, инвентаризация, рецепты, продажа в магазине | ✓ | ✓ | — |
| Новые складские позиции, их удаление/архив | ✓ | — | — |
| Сотрудники, настройки (оплата при получении, точка магазина), «О нас», зоны доставки и их границы, интервалы, журнал действий | ✓ | — | — |

Права проверяются на сервере (DRF permissions + фильтрация queryset по курьеру).
Вход сотрудника выдаёт Bearer-токен со сроком действия 72 ч (`STAFF_TOKEN_TTL_HOURS`), выход его удаляет;
частота попыток входа ограничена (10/мин). Все действия сотрудников пишутся в `audit_logs`.

## 6. Безопасность и эксплуатация

* Секреты только в переменных окружения; без `DJANGO_SECRET_KEY` в продакшен-режиме сервер не стартует.
* Публичный статус заказа — по секретному токену или номер + телефон; не раскрывает внутренние данные.
* Персональные данные: доступ к клиентам — только у владельца и флориста, курьер видит лишь
  адрес и контакты своих доставок (без сумм). БД, бэкапы и медиа хранятся в томах на вашем
  сервере, внешних облачных сервисов нет — стенд готов к размещению у российского
  хостинг-провайдера (152-ФЗ, локализация ПДн).
* Ошибки API — единый формат `{"error": {"code", "message", "details"}}`.
* Резервные копии — сервис `db-backup` (pg_dump, ротация).
* Throttling: вход сотрудников, вход покупателей (12 запусков/мин, 120 опросов/мин), оформление заказа.
* Токен сессии покупателя — 32 байта `secrets`, в БД только SHA-256; выдаётся один раз после
  подтверждения в мессенджере; «Выйти на всех устройствах» удаляет все сессии клиента.

## 7. Расширение (не входит в MVP)

Архитектура допускает добавление без переделки ядра: новый платёжный провайдер (CloudPayments,
Т-Банк и т.п.) — класс в `payments/providers` + регистрация; онлайн-касса — через
`fiscal.py`; несколько магазинов — поле `location` уже есть в `stock_balances`; лояльность,
подписки — отдельные модули поверх `customers` и `orders`.
