# Безопасность сайта «Цветы Урала»

Что угрожает интернет-магазину, чем сайт защищён «из коробки» и что нужно сделать владельцу
перед запуском. Проверка настроек в один клик: **Админка → Настройки → «Безопасность»**
(или `docker compose exec backend python manage.py security_check`).

## 1. Чек-лист владельца перед запуском

1. **Пароль владельца.** Войдите `owner` / `owner12345` → сайт сразу попросит сменить пароль
   (Админка → «Сменить пароль», не короче 10 символов, не из словаря, не похожий на логин).
2. **Сотрудники.** Демо-логинов флориста и курьеров больше нет (их удаляет миграция). Новых
   сотрудников заводит только владелец: **Админка → Сотрудники → «+ Сотрудник»** — свой логин и
   пароль каждому. Уволился — снимите галочку «Доступ активен» или нажмите «Удалить» (его вход сразу перестаёт работать).
3. **Секреты.** `docker compose run --rm --no-deps backend gen-secrets` → вставьте строки в `.env`
   (`DJANGO_SECRET_KEY`, `PAYMENT_SIMULATOR_SECRET`, `BOT_SERVICE_TOKEN`, `POSTGRES_PASSWORD` — см. п. 4).
   Файл `.env` никому не пересылайте и не выкладывайте в Git.
4. **Пароль базы данных.** Если база уже создана, пароль меняют сначала в самой базе, затем в `.env`:
   ```bash
   docker compose exec db psql -U flowers -d flowers -c "ALTER USER flowers WITH PASSWORD 'НОВЫЙ_ПАРОЛЬ';"
   # затем POSTGRES_PASSWORD=НОВЫЙ_ПАРОЛЬ в .env и
   docker compose up -d --force-recreate
   ```
5. **Боевой режим:** `PRODUCTION=true`, домен и HTTPS — по инструкции [DEPLOY.md](DEPLOY.md).
6. **Демо-данные:** `docker compose exec backend python manage.py clear_demo --yes`
   (демо-заказы и демо-покупатели; `--catalog` — ещё и демо-товары).
7. **Оплата:** касса RollyPay и ключи (`PAYMENT_PROVIDER=rollypay`, `ROLLYPAY_TEST_MODE=false` после проверки) или только оплата при
   получении — в боевом режиме тестовый симулятор оплаты автоматически выключается.
8. **Резервные копии** (`./backups`) регулярно копируйте с сервера в другое место.

## 2. Угрозы и защита

| Угроза | Как защищено |
|---|---|
| **Подбор пароля к админке** | 5 неверных паролей подряд → вход под этим логином закрыт на 15 мин (с любых IP) (`LOGIN_MAX_FAILS`, `LOGIN_LOCK_MINUTES`); лимит 10 попыток/мин с IP; одинаковый ответ «неверный логин или пароль» (не выдаёт, какие логины есть); пароли — только хеши PBKDF2; требование 10+ символов и проверка по словарю популярных паролей; стандартный пароль → принудительная смена |
| **Кража сессии сотрудника** | у каждого устройства свой вход (можно одновременно с телефона и компьютера), он живёт 72 ч (`STAFF_TOKEN_TTL_HOURS`); «Выйти» завершает вход на этом устройстве; смена пароля, отключение и удаление сотрудника сразу завершают входы на всех устройствах; в боевом режиме cookies только по HTTPS (Secure, HttpOnly, SameSite). Токен входа сотрудника хранится только в HttpOnly-cookie `cu_staff` (JavaScript страницы его не видит, поэтому даже внедрённый скрипт не унесёт вход на другое устройство); изменения по cookie принимаются только с заголовком `X-Requested-With: fetch` (защита от CSRF) + `SameSite=Strict`. Старый токен из `localStorage` один раз переносится в cookie (`/admin/auth/adopt`) и стирается. Двухфакторный вход — в планах |
| **Перегрузка (DoS) и парсеры** | общий лимит API: 180 запросов/мин и 3000/ч с одного IP (`THROTTLE_BURST`, `THROTTLE_SUSTAINED`); отдельные лимиты: оформление заказа 6/мин и 20/ч, поиск заказа 10/мин, поиск адреса 30/мин и 600/сутки, смена пароля 5/мин; ответ 429 «слишком много запросов» |
| **Медленные соединения (Slowloris), огромные запросы** | Caddy обрывает соединения, не приславшие заголовки за 10 с; заголовки ≤ 32 КБ, тело ≤ 12 МБ; gunicorn: таймаут 30 с, лимиты на строку и заголовки, потоковые воркеры, периодический перезапуск процессов; Redis ограничен 256 МБ; логи Docker с ротацией (диск не переполнится) |
| **Массированный DDoS (гигабиты трафика)** | такой поток «кладёт» канал сервера до того, как дойдёт до сайта — это решается только снаружи: подключите бесплатный **Cloudflare** или **DDoS-Guard** (прокси-режим) и раскомментируйте `trusted_proxies` в `deploy/Caddyfile`, чтобы лимиты считали настоящий IP покупателя |
| **Спам-заказы, «бронирование» всего склада** | скрытое поле-ловушка для ботов (honeypot); лимиты на оформление; у одного телефона не больше 3 неоплаченных/неподтверждённых заказов (`MAX_PENDING_ORDERS_PER_PHONE`); резерв неоплаченного заказа снимается автоматически по истечении времени |
| **Подмена цены / суммы заказа** | цена, скидки, доставка и наличие считаются только на сервере; данные из браузера (цены, суммы) игнорируются; повторная отправка формы не создаёт дубль (ключ идемпотентности) |
| **Поддельное уведомление об оплате** | RollyPay: обязательная подпись HMAC-SHA256 (`X-Signature`, `signing_secret`) с отметкой времени, затем статус и сумма запрашиваются у API RollyPay; тестовый платёж не подтверждает заказ в боевом режиме. ЮKassa: сервер не верит телу уведомления, а заново запрашивает платёж у ЮKassa по API; симулятор — подпись HMAC-SHA256; повторы уведомлений обрабатываются один раз; оплата сверяется с суммой заказа |
| **SQL-инъекции** | все запросы к базе — через ORM Django с параметрами, «сырого» SQL из пользовательских данных нет |
| **XSS (внедрение скриптов)** | React экранирует любой текст; строгая Content-Security-Policy (`frontend/middleware.ts`): на каждый показ страницы — новый nonce, выполняются только скрипты с ним и загруженные ими (Яндекс Карты, `'strict-dynamic'`), без `'unsafe-inline'` и `'unsafe-eval'`; фото из `/media` отдаются с CSP `sandbox` (ничего не исполняется) |
| **Кража входа покупателя** | токен сессии и незавершённого входа — только в HttpOnly-cookie (`cu_customer`, `cu_login`), в ответах API и в `localStorage` их нет; статус входа — только POST (токен не попадает в адрес и журналы); подтверждённый, но не забранный за 10 минут вход сгорает; журнал Caddy не пишет заголовки `Cookie`, `Set-Cookie`, `Authorization`, `X-Customer-Token` |
| **Кликджекинг, встраивание сайта в чужие страницы** | `X-Frame-Options: DENY`, `frame-ancestors 'none'` |
| **Перехват трафика** | HTTPS (Let's Encrypt, автопродление), HSTS 1 год, редирект с http и www |
| **Вредоносные файлы при загрузке фото** | принимаются только настоящие JPEG/PNG/WEBP (проверка содержимого, а не расширения); защита от «фото-бомб» (≤ 40 Мп); фото пересохраняется — удаляются EXIF (в т. ч. GPS) и любые вложенные данные; имя файла случайное; размер ≤ 12 МБ |
| **Сканеры уязвимостей** | пути `/wp-*`, `*.php`, `/.env`, `/.git`, `/phpmyadmin` и т. п. сразу получают 404 на уровне Caddy; технический Django admin и Swagger в боевом режиме выключены (`DJANGO_ADMIN_ENABLED`, `API_DOCS_ENABLED`) |
| **Утечка ошибок и версий** | `DEBUG` в боевом режиме запрещён (сервер не стартует с `PRODUCTION=true` + `DJANGO_DEBUG=true`); заголовки `Server`/`X-Powered-By` скрыты; ошибки отдаются без трассировок |
| **Секретные ссылки в журналах** | ссылки на заказ, оплату и корзину содержат секретный токен, вход покупателя — временный токен (сайт передаёт его в теле POST-запроса, а не в адресе). В журналах Caddy, gunicorn и Django токены заменяются на `***` (`deploy/Caddyfile`, `backend/config/log_masking.py`); Caddy не пишет в журнал заголовки `Authorization` и `Cookie`. Журналы доступны только `root` на сервере |
| **Потеря данных** | каждые 24 ч — копия базы (`backups/flowers_*.dump`, 7 последних) и архив фото (`backups/media_*.tar.gz`, 3 последних); восстановление проверено (`pg_restore --clean` поверх рабочей базы, распаковка фото). Копии нужно регулярно уносить с сервера (см. OWNER_GUIDE.md) |
| **Доступ к базе и Redis снаружи** | порты PostgreSQL и Redis наружу не открыты; backend и сервер сайта слушают только `127.0.0.1`, снаружи доступны лишь 80/443 через Caddy (проверено снаружи: 3000, 5432, 6379, 8000, 2019 закрыты) |
| **Права сотрудников** | роли проверяются на сервере в каждом запросе: курьер видит только свои доставки, флорист не видит цены закупки, настройки, сотрудников, статистику и возвраты; все важные действия пишутся в журнал (Админка → Журнал) |
| **Перерасход ключа Яндекса** | поиск адресов ограничен по IP и в сутки (`YANDEX_GEOCODER_DAILY_LIMIT=900`), при превышении — бесплатный OpenStreetMap |
| **Боты Telegram / ВК** | сервисный токен сравнивается в постоянное время; канал определяется сервером; вход покупателя на сайт подтверждается только кнопкой в мессенджере |
| **Уязвимые библиотеки** | зависимости обновлены (Next.js 15.5, React 19.1, Django 5.2, DRF 3.18); `npm audit` и `pip-audit` — 0 известных уязвимостей. Обновляйте проект раз в 1–2 месяца |

## 3. Если что-то случилось

* **Забыли пароль владельца:**
  `docker compose exec backend python manage.py changepassword owner`
* **Сотрудник подозревает, что пароль узнали:** владелец → Сотрудники → нажмите на сотрудника →
  «Новый пароль» → «Сохранить» (все сеансы этого сотрудника завершатся).
* **Заблокирован вход после неверных попыток:** подождите 15 минут или смените пароль командой выше.
* **Сайт под нагрузкой:** `docker compose logs --tail 200 caddy backend` — видно IP и пути;
  включите Cloudflare «Under Attack Mode» или ужесточите `THROTTLE_BURST` в `.env`.
* **Утёк `.env`:** сгенерируйте новые секреты (`gen-secrets`), смените пароль базы (п. 4),
  перевыпустите токены ботов и ключи кассы (RollyPay: api_key и signing_secret — через поддержку) в их кабинетах, перезапустите контейнеры.

## 4. Настройки безопасности (`.env`)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PRODUCTION` | `false` | боевой режим: HTTPS-cookies, HSTS, выключены Swagger, Django admin, симулятор оплаты и демо-надписи |
| `LOGIN_MAX_FAILS` / `LOGIN_LOCK_MINUTES` | `5` / `15` | блокировка входа после неудачных попыток |
| `THROTTLE_BURST` / `THROTTLE_SUSTAINED` | `180/min` / `3000/hour` | общий лимит запросов к API с одного IP |
| `THROTTLE_INTERNAL_EXEMPT` | `true` локально, `false` в боевом | не ограничивать запросы из локальной сети (нужно для тестов на своём компьютере) |
| `TRUSTED_PROXY_COUNT` | `1` | сколько прокси перед сайтом (Caddy = 1; Caddy + Cloudflare — оставьте 1 и настройте `trusted_proxies`) |
| `MAX_PENDING_ORDERS_PER_PHONE` | `3` | лимит неоплаченных заказов на один телефон (`0` — без лимита) |
| `YANDEX_GEOCODER_DAILY_LIMIT` | `900` | сколько платных запросов к Яндекс Геокодеру в сутки |
| `DJANGO_ADMIN_ENABLED` / `API_DOCS_ENABLED` | `true` локально, `false` в боевом | технический Django admin и Swagger |
| `STAFF_TOKEN_TTL_HOURS` | `72` | сколько часов действует вход сотрудника |
